## First use

This applies only to reports generated by a release that carries it, after that release's recorded activation time. It
does not apply to any report issued before. Earlier reports keep their labels and their recorded reasons. No
selected-observation identity is ever computed or invented for an issued report. Activation and first-run times are
recorded from the window receipts, never from this text.

## Why

Under contract v2, LG's observation identity was the selected observation day plus the report's input digests
(`input_sha256`, `input_selection_sha256`). Both digests embed the scored day's as-of instant, and both cover every
byte of every carrier file. So when the GNSS files did not advance, LG recorded **revised the same observation**
(`REVISED_SAME_EPOCH`) on every day instead of **repeated input**.

The confirmation decision was still right, because neither label counts as a new observation. The stated reason and the
public line were wrong.

## What changes

LG's repeat and revision are now judged on what the selected value actually consumed.
- **The scope:** the selected observation's **dependency closure**. The whole report input no longer decides it.
- **The identity:** `measurement.observation_content`, a digest written by a runner-side module
  (`lg_observation_identity.py`). It is not part of the LG operator, so the operator identity, every baseline binding
  and every value stay as they are.

**What the closure covers.** It comes from the operator's composition: interpolation, then Savitzky-Golay smoothing over
7 rows, a velocity difference, the per-triangle strain solve, the strain-rate difference, the commutator norm, and the
maximum over triangles. So the selected value depends on:
- each carrier station's E/N values on the **five daily grid rows either side** of the selected epoch;
- for a missing row inside that window, the two real samples it is interpolated from, even when they lie outside the
  window;
- the stations' catalog positions, order and triangles;
- the fixed origins and the operator identity.

**What is excluded:**
- the report date and as-of instant;
- the start of the rolling 90-day window;
- file times and whole-file digests;
- every other row;
- Up, uncertainties and headers.

The existing whole-file digests stay in the record as provenance. They are no longer read as observation identity.

**How the identity is computed:**
- Each retained file is read once, its digest checked against the producer's manifest, and parsed from those same
  bytes.
- The selected value is then recomputed **from the closure alone**, and must equal the producer's value exactly before
  the identity is recorded as known.
- Anything unverifiable gives an identity of **unknown**. An unknown identity blocks confirmation. It never removes the
  LG value or changes its score.

| LG step | v2 (until this release) | v3 |
|---|---|---|
| a later observation day | new observation | new observation (unchanged) |
| same day, same files | **revision** (the as-of moved) | **repeated input** |
| same day; a file changed only outside the closure | revision | repeated input |
| same day; a value inside the closure changed | revision | revision |
| no recorded identity, or a schema, encoding, epoch or digest that does not bind | unknown | unknown |

## Transition cost (stated in advance)

The contract moves from v2 to `method-comparability-v3`, through the existing regime reset. Codex's ruling was not to
amend the identity rule silently under v2. A row issued without the new identity, compared within the same regime,
could otherwise block confirmation for several days.

- **No v2 report day counts toward a v3 confirmation.** On the first v3 run, every region at WATCH or above records
  `REPORT_DAYS_BELOW_REQUIRED:REGIME_TRANSITION` and is not confirmed. That includes regions confirmed by THD alone. It
  is a disclosed rule change, not a data outage.
- From the second v3 run, regions confirm normally, when every included method shows a new observation.
- No score, weight, tier or method inclusion changes. LG stays enabled.
- A v2 row is never compared with a v3 row. The regime boundary stops the chain first, so no old unknown identity
  carries across.

## What a reader sees

- **Report JSON:**
  - `measurement.observation_content` gives the schema, encoding, status, digest, epoch, window and counts;
  - `persistence.regime.confirmation_rule` reads `observation-update-confirmation-v2`;
  - LG's `observation_updates.basis` reads `RETAINED_LG_SELECTED_OBSERVATION_CONTENT`.
- **The run summary of the LG operation** keeps the full canonical record whose digest is recorded, so the digest can be
  checked without re-reading the provider files.
- **The Pages card and the raw-history download:** their wording is unchanged. With unchanged files, LG now reads
  "repeated input (the same observation as the previous report)" where it read "revised". On the first v3 day the line
  names the rule change.
- **The hosted explorer:** unchanged code. It shows the new version strings and reasons as recorded.
